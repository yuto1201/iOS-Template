# X Post Material

ユーザーはXで、作っているアプリの投稿を運用している。投稿はGrok Botが、GitHubのそのアプリのリポジトリの`main`にある`XPosts/`を読んで行う。このスキルは、その材料を機能開発のついでに残す（D-096）。

Xへの投稿、文面の最終決定、投稿済みの記録はGrok Botが行う。このスキルはそれらを扱わない。

## いつ使うか

- 画面のある機能を作っている途中、またはその機能IssueのPRを出す前に、Claudeが「この機能はXに投稿する価値がある」と判断したとき。判断はClaudeが行い、ユーザーに確認しない。
- 対象は、ある程度完成して操作できる機能。ある程度完成した機能は、すべて公開してよい。
- 次のものには使わない：画面のない作業（workflow、tool、文書だけ）、まだ動かない途中の画面、テンプレート自身の`TemplateApp`。
- 投稿は1日1つ程度なので、材料はたまっていってよい。迷ったら残す。

投稿する価値の目安：

- 見た目で伝わる（画面、アイコンの一覧、たくさん並んだ画像、アニメーション）。
- 「こんなことができる」と一言で言える。
- 工夫した点、意外な点、作るときに苦労した点がある。

## 重ならないようにする

材料を作る前に、既存の`XPosts/`のすべての`post.json`と`post.md`を読む。

- 同じ機能で、同じ推しどころの材料がすでにあれば、作らない。
- 同じ機能でも、新しい推しどころ（新しい見た目、新しい使い方）がある場合だけ作る。そのときは`post.json`の`related`に、近い既存のフォルダ名を書く。
- 1つの機能に面白い点が2つあれば、フォルダを2つ作り、互いを`related`に書く。1つの`post.md`に推しどころを詰め込まない。

## フォルダ

```text
XPosts/
  README.md                       # Grok Botへの案内（最初に一度だけ作る）
  2026-10-25-icon-list/
    post.md
    post.json
    01-icon-grid.png
    02-detail.png
    03-scroll.mp4
```

- フォルダ名は`<YYYY-MM-DD>-<サブタイトル>`。日付は材料を作った日で、必ず入れる。サブタイトルは内容を表す英小文字、数字、ハイフン（例：`icon-list`、`tent-ar-preview`）。日本語を使わない。
- 同じ日に同じサブタイトルが重なるときは、`-2`のように番号を足す。
- ファイル名は英小文字、数字、ハイフンと、`.png`、`.jpg`、`.mp4`。並べたい順に`01-`のような番号を付ける。
- `XPosts/README.md`がまだなければ、[templates/README.md](templates/README.md)をそのまま写して作る。中身を書き換えない。

## post.md

日本語だけで書く。[templates/post.md](templates/post.md)の見出しをそのまま使う。

- **事実**：作った機能が何をするか、どう使うか、どの画面にあるか。可能な限り具体的かつ詳細に書く（数、名前、操作の順番、前と何が変わったか）。Grok Botはこの欄だけを機能の説明として使うので、実際の画面で確かめたことだけを書く。予定や未実装の機能を書かない。
- **推しどころ**：どこが面白いのか、工夫した点、意外な点、作るときに苦労した点。言い回しの案を書いてもよい。
- **画像と動画**：ファイルごとに、何が写っているか、どこを見てほしいか。
- 宣伝の決まり文句、ハッシュタグ、絵文字は書かない（Grok Botが文面を決める）。

## post.json

```json
{
  "schemaVersion": 1,
  "app": "CampPocket",
  "title": "アイコンの一覧",
  "createdAt": "2026-10-25",
  "issue": 123,
  "related": [],
  "media": [
    {"file": "01-icon-grid.png", "kind": "image", "description": "全24種類のアイコンを一覧にした画面"},
    {"file": "03-scroll.mp4", "kind": "video", "description": "一覧をスクロールして詳細を開く12秒の動画"}
  ]
}
```

- キーはこの順番で、ほかのキーを足さない。`app`はアプリの表示名、`createdAt`はフォルダ名の日付と同じ、`issue`は機能Issueの番号。
- `media`はフォルダの中のすべての画像と動画を、1つずつ書く。1つ以上の画像を必ず入れる。
- 投稿済みかどうかは書かない（Grok Botが自分の側に残す）。

## 画像と動画を撮る

- 撮るのは、そのリポジトリの専用Simulator（D-063、D-070、D-079）だけ。新しいdeviceを作らない。検証（`ios-verify`）で撮った画像を使い回してよい。日本語の表示で撮る。
- 画像は、説明が分かるものを何枚か。アイコンならアイコンを並べた画像、たくさん並んだ画像など、関係するものは何でもよい。Xの添付は画像4枚までなので、4枚より多く撮ってGrok Botに選ばせてよい。
- 動画は`xcrun simctl io <UDID> recordVideo --codec=h264`で撮り、mp4にする。1本5秒以上30秒以下。できれば多めに撮るが、撮れない場合に無理はしない。
- アニメーションが推しどころの投稿では、そのアニメーションを録画する作業を必ず行う。
- 長すぎる動画は`ffmpeg -ss <開始> -t <長さ> -i in.mp4 -c:v libx264 -an out.mp4`で切る。
- 秘密、認証情報、個人情報、実在の人の名前や連絡先、通知やほかのアプリの内容を写さない。必要ならサンプルのデータで撮る。

## 機能のPRに入れる

- 材料は、その機能IssueのPRの同じブランチにcommitする。投稿の材料のためだけのIssueは立てない（D-096）。`XPosts/`の材料は、Acceptance criteriaの範囲外への機能の追加として扱わない。
- 検証のHeadを決める前に入れる。あとから入れるとHeadが変わり、検証をやり直すことになる。
- commitする前に、秘密、認証情報、個人情報が入っていないかを、次のすべてで確かめ、見つけたら取り除く（撮り直す、書き直す、ファイルを消す）：
  - `post.md`の事実、推しどころ、画像と動画の説明。
  - `post.json`のすべての値（特に`title`と`media`の`description`）。
  - すべての画像と動画を、1枚ずつ、動画は最初から最後まで見る。
  - 対象：API keyやtoken、password、署名や課金の情報、メールアドレス、電話番号、住所、実在の人の名前や顔、ユーザーのデータ、通知やほかのアプリの内容、このMacのユーザー名やpath。
- 次に、書式を確かめる：

```sh
tools/check-x-posts.sh XPosts
```

- 機能のPRがmergeされると、Grok Botが`main`から読む。

## 報告

材料を残したら、ユーザーへ日本語で短く報告する：フォルダ名、推しどころを一言、画像と動画の数。残さないと判断した機能は報告しない。
